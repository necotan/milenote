# CLAUDE.md

## Language rules

- Respond to the user in Japanese.
- Commit messages: first line in English, all following lines in Japanese.
- Write code comments in Japanese.
- Use English for variable names, function names, file names, and translation keys.
- Write `ja.json` values in Japanese and `en.json` values in English.

## Project

milenote: a car maintenance-cost tracking app (Next.js App Router + Supabase).

## Commands

- `npm run dev` / `npm run build` / `npm run start`
- `npm run lint`: ESLint
- `npx tsc --noEmit`: type check (no npm script)
- `npx supabase <command>`: Supabase CLI (see `manuals/supabase_migrations.md`)
- There is no test suite.

## After every change

- Run `npm run lint` and `npx tsc --noEmit`.
- If locales changed, confirm `ja.json` and `en.json` have the same keys. `tsc` does not check keys, and `t()` shows the raw key when one is missing.
- For UI changes, check both PC and smartphone layouts.
- For new queries or deletes, re-check the car status and delete rules below.

## Layout

- `app/`: pages (App Router). `proxy.ts`: redirects unauthenticated requests to `/login`.
- `components/`: feature components. `components/ui/`: shared UI.
- `lib/`: business logic. `lib/hooks/`: SWR data hooks (`useCars`, `useRecords`, etc.). `lib/i18n/`: translations.
- `utils/`: generic helpers (Supabase client, car images, public routes, etc.)
- `supabase/migrations/`: schema changes. `manuals/`: operation guides.
- `docs/`: design docs tracked in git. Read the one for the area you change:
  - `data-model.md`: tables, constraints, server-side functions
  - `delete-design.md`: car status, status filtering, delete rules
  - `stored-values.md`: slugs stored in the DB
  - `security-design.md`: RLS, auth, Storage, output handling
  - `design.md`: color, surfaces, shape, typography
  - `ios-pwa.md`: safe area, status bar, modal overlays on iOS
- Other files in `docs/` are local-only notes, mostly written by Claude in past sessions (git-ignored; absent in fresh clones and worktrees). Some are outdated. Use them only as a reference when stuck; the code, this file, and the design docs take precedence.
- File names: components in PascalCase, everything else in camelCase. Files generated by shadcn in `components/ui/` keep their lowercase names (e.g. `button.tsx`).

## Coding

- TypeScript. Do not use `any` or omit type definitions.
- Function components with Hooks.
- NEVER hard-code values from `.env.local`.

## Comments

- Write only why: the reason for a choice, workarounds for browser or library quirks, and relations to DB constraints.
- Do not write what the code, names, or JSX already say (e.g. "ハンバーガーメニュー", "〜処理", "〜コンポーネント", "金額"). If there is no why to explain, write no comment.
- If the same explanation would go in two places, consider sharing the code instead.
- No decorative characters such as `---`, `===`, `***`.

## i18n

- Use translation keys for all UI text. Do not write Japanese or English directly in JSX.
- Add every new string to both `lib/i18n/locales/ja.json` and `lib/i18n/locales/en.json` in the same change.
- Key naming: `<page>.<element>` in snake_case (e.g. `garage.car_status_active`). Shared text goes in `common`, `nav`, `categories`, `subcategories`, `fuel_types`, `wishlist_genres`, `wishlist_statuses`.
- Use `useTranslation()` from `lib/i18n/index.tsx`. Placeholders use `{{name}}`.

## Database (Supabase)

- NEVER run mutating SQL (CREATE / ALTER / DROP / INSERT, etc.) in the Supabase Dashboard SQL Editor; it drifts from the local migrations. Use the Dashboard for SELECT only.
- MUST make every schema change (tables, columns, functions, triggers, RLS policies, indexes, Storage) through a file in `supabase/migrations/`. Procedure: `manuals/supabase_migrations.md`.
- Store English slugs, never display text (`docs/stored-values.md`). Allowed values have CHECK constraints, so adding one needs a migration (`docs/data-model.md`).

## Cars and car-linked data

Status semantics, per-screen filters, and the checklist: `docs/delete-design.md`.

- `cars.status`: `pending`, `active`, `archived` (former car, in stats), `archived_excluded` (former car, out of stats). There is no `deleted` status. Deleting a car is a physical delete; do not add a soft delete.
- MUST filter cars and car-linked data (records / recurring_costs / wishlists) by car `status` in every list, aggregate, export, and batch job (stats: `active` + `archived`; input: `active`). `useCars` and `useRecords` return all rows for the user, so filter before use. Why: hidden cars' records once leaked into the record list and CSV export.
- MUST clean up children and Storage when deleting a car or any other parent. Children are `ON DELETE CASCADE` on `car_id`; car images in the `cars` bucket must be removed in code. Check the FK `ON DELETE` behavior whenever adding a parent-child relation. Why: deletes once left child data behind.

## Git workflow

- Do not run `git checkout -b`, `commit`, `push`, PR creation, `merge`, or `pull`. The user runs them.
- At the start of work, propose a branch name (`feature/xxx` or `fix/xxx`). Say no branch is needed only when the change is visual only (CSS, text, colors) with no logic impact, and small enough to review the diff by eye.
- After code changes, run `git status` and `git diff` (plus `git diff --staged` if anything is staged), then propose a commit message based on the actual diff.

## Commit messages

| Prefix | Use |
|---|---|
| fix | Bug fix |
| hotfix | Critical bug fix |
| add | New file or feature |
| update | Feature change (not a bug) |
| change | Spec change |
| clean | Cleanup, refactoring |
| disable | Disable, comment out |
| remove | Remove a file or feature |
| upgrade | Version upgrade |
| revert | Revert a change |

- Line 1: `<prefix>: <summary in English>`.
- The body is optional. For a small change that line 1 fully describes, write line 1 only. Otherwise add a blank line and 1 to about 4 Japanese bullets; do not pad to reach 4.
- Bullets name the concrete files, components, properties, or storage targets changed and how. Do not explain causes or background.
- Only when the user explicitly asks for causes or background, write prose with the root cause (file and line) and the fix approach.

```
fix: typo in garage empty state text
```

```
fix: skeleton UI misaligned with actual cards in maintenance list

- ローディング中のグリッド外枠に gridWrapperRef を付与
- 並び替え、絞り込み、表示設定ボタン行に maxWidth: gridContentWidth を適用
- スケルトンのグリッドを固定Tailwindクラスから実カードと同じ gridStyle に変更
- スケルトンカードの表示枚数をハードコードの3件から gridColumns に変更
```
